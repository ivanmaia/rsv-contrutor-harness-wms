Três regras que não se quebram

1

Nunca rode git push para os repos nem git subtree à mão: quem envia é o ws push.

2

Dentro de repos/<repo>/, não crie nem altere .specify/, specs/ e .claude/skills/speckit-*.

3

Durante uma feature ou um bug, não altere o harness: tools/, .specify/, .claude/, AGENTS.md, CLAUDE.md e docs/adr/. Achou um problema? Registre para o time do harness.

E A REGRA DOS PRs

Os PRs saem pelo harness. O do workspace é completado por último, e a branch de origem não se apaga ao completar.

Harness WMS · 41/63

As regras vêm da camada 1 e do AGENTS.md. A primeira: o envio passa pelo ws push, que sabe separar as mudanças de cada repo; nada de git push, git subtree à mão nem git pull numa branch de trabalho. A segunda: esses arquivos dentro de repos/repo são do harness; o ws push recusa a branch (ws: GUARDA) se eles mudarem, e remover é permitido. CLAUDE.md, AGENTS.md, o resto de .claude/ e .github/ do repo podem ser editados: é onde vão as convenções do repo. A terceira corrige a v1: o AGENTS.md lista tools/, .specify/, .claude/, AGENTS.md, CLAUDE.md e docs/adr/ como harness, e a camada 1 ainda lista só os quatro primeiros (pendência registrada). A regra nova dos PRs: abertos pelo harness, ao ramo de teste no fim do envio e ao main com /ws-pr-main; o do workspace é aberto junto e completado por último, nada impõe a ordem mas a política é de cada repo; não apague as branches de origem.
