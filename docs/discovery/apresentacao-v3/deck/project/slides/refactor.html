Um refactor, do relato ao PR

1

/speckit-refactor-assess

Cria a branch refactor/<slug>. Diz o que não pode mudar e planeja os testes de caracterização.

2

Leia o assessment.md

Aprove exceção aos testes só com uma verificação que a substitua. Falta de tempo não vale.

3

/speckit-refactor-apply

Primeiro os testes que fixam o comportamento atual, num commit próprio. Depois, o refactor.

4

/speckit-refactor-verify

Build, testes e a conferência de que os de caracterização não mudaram. Falha nova barra.

A REGRA

O comportamento observável não muda. Se mudar ele ou um contrato, não é refactor: reclassifique. Mover código entre repos e migrar para o AWX ainda não entram.

O ENVIO

Atlas, commit e envio, e a mesma oferta dos PRs da feature.

Harness WMS · 34/63

Refactor é mudar a estrutura sem mudar o que o código faz (constitution VII). O teste de caracterização chama o código como ele está e afirma o que ele devolve hoje, mesmo que pareça estranho: o objetivo é fixar, não corrigir; usa o framework e as abstrações que o repo já tem. A exceção serve só para trecho que não dá para testar sem um refactor anterior, não para falta de tempo, e precisa da sua aprovação com a verificação substituta. Testes que já falhavam ficam registrados como linha de base no apply.md e não barram; falha nova barra (constitution III). Dívidas de conformidade do repo, como as do AWX, não se aplicam num refactor e vão como fora de escopo. Se o diagnóstico concluir que o comportamento muda, reclassifique como feature ou bug. Envio e PRs como na feature. Mover código entre repos e migrar para o AWX ainda não entram. Tempo: 2 min
